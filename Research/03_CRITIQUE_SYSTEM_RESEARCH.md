# Atelier Critique System Research

# Research Document Context

These files are created for **Atelier / Designers Hub**, a creative-professional community platform being reworked around forum discussions, structured critique, help posts, resources, profiles, dashboards, uploads, search, reputation, settings, moderation, and future admin systems.

The purpose of these files is not to provide final answers yet. Each file clearly defines **what data must be researched**, **why it matters**, **what questions to answer**, and **what output should be produced** before implementation decisions are made.

Use these files as research briefs for ChatGPT, Codex, manual web research, competitor analysis, product planning, and implementation planning.


## Purpose

This research defines Atelier's most important differentiator: a structured critique space for creative work. The goal is to make critique more useful than a normal comment section.

## Main research objective

Research how design critique works in studios, schools, online communities, and professional review settings, then translate that into a product system for Atelier.

## Data to research

### 1. What makes critique useful

Research the qualities of strong design critique:

- Specificity.
- Context awareness.
- Actionability.
- Respectful tone.
- Connection to project goals.
- Discipline-specific vocabulary.
- Explanation, not just opinion.
- Awareness of constraints.
- Difference between taste and objective problem.

Collect examples of:

- Excellent critique comments.
- Weak critique comments.
- Harmful critique comments.
- Before/after improvements caused by critique.

### 2. Critique request structure

Research what the creator must provide before asking for critique.

Data to collect:

- Project title.
- Discipline.
- Project type.
- Target audience.
- Design goal.
- Current problem.
- Constraints.
- Tools used.
- Stage of work: concept, draft, final, revision.
- What feedback is requested.
- What feedback is not requested.
- Images/assets.
- Reference/inspiration if relevant.

Research whether critique posts should require structured fields instead of only a body text field.

### 3. Critique comment structure

Research how feedback comments should be shaped.

Possible comment fields:

- What works well.
- What is unclear.
- Main issue.
- Suggested improvement.
- Reason behind the suggestion.
- Priority: minor / important / critical.
- Category: layout / color / typography / hierarchy / usability / branding / concept / execution.
- Confidence level.
- Optional visual annotation.

Research:

- Should comments be freeform or guided?
- Should critique categories exist?
- Should users mark comments as useful?
- Should authors respond to critique?
- Should critique be threaded?

### 4. Visual critique and uploads

Research features needed for visual work:

- Image gallery.
- Before/after comparison.
- Version history.
- Revision uploads.
- Annotation/pin comments later.
- Fullscreen preview.
- Asset metadata.
- Safe upload limits.
- Image compression.
- Thumbnail generation.

Research how much should be built now versus later.

### 5. Revision and improvement loop

Research how to make critique feel like progress, not judgment.

Data to collect:

- How revisions should attach to the original critique post.
- How users should show improved versions.
- Whether a critique can be marked as revised.
- Whether contributors get credit if their feedback helped.
- Whether the author can mark feedback as implemented.
- How before/after improvements should be displayed.

### 6. Critique quality standards

Research how to define good and bad critique.

Good critique examples:

- Specific.
- Respectful.
- Explains why.
- Connects to the user's goal.
- Gives a possible direction.
- Does not rewrite the entire project without consent.

Bad critique examples:

- “Looks bad.”
- “Make it pop.”
- Personal insults.
- Vague taste comments.
- Unsolicited harshness.
- Overly generic AI-sounding feedback.
- Feedback unrelated to the requested area.

### 7. Critique incentives

Research how to encourage people to give good critique.

Data to collect:

- Should useful critique earn reputation?
- Should the author mark feedback as helpful?
- Should other users vote on critique comments?
- Should high-quality critics get badges?
- How to avoid people farming critique points?

## Questions this research must answer

1. How is critique different from discussion?
2. What fields should a critique post require?
3. What does a good critique comment look like?
4. Should critique comments be structured?
5. Should image annotation exist now or later?
6. Should revisions be part of the first version?
7. How should before/after improvement be shown?
8. How should helpful critics be rewarded?
9. How should low-quality critique be handled?
10. What is the minimum lovable critique system for launch?
